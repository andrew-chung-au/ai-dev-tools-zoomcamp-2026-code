# Issue #6 — Step 10: Alembic database migrations

Replaces the FastAPI backend's `Base.metadata.create_all()` startup schema
creation with version-controlled Alembic migrations, per issue #6
("Table Ready Deployment: [Backend Database Migrations] Introduce Alembic
for database migrations"). Continues the deployment line started in issue
#5 ([[issue-005_step-09_integration-and-e2e-tests]]).

## Dependency check-in

`AGENTS.md` requires asking before adding a `pyproject.toml` dependency.
Confirmed with the user before adding `alembic>=1.13` as a **main**
dependency (not dev-only), since `alembic upgrade head` must run at
container/production startup, not just in local dev.

## What changed

- **`pyproject.toml` / `uv.lock`** — added `alembic>=1.13`.
- **`alembic.ini`** (repo root) + **`backend/alembic/`** (`env.py`,
  `script.py.mako`, `versions/`) — `uv run alembic init backend/alembic`,
  then:
  - `backend/alembic/env.py` imports `Base` from `backend/db.py` and
    `backend/orm_models.py` (so `target_metadata` reflects the real ORM
    schema) and overrides `sqlalchemy.url` from the `DATABASE_URL`
    environment variable when set — the same variable
    `backend/config.py` reads — falling back to the `alembic.ini` value
    only for local `alembic revision --autogenerate` runs with no env var.
  - `alembic.ini`'s `sqlalchemy.url` left as a local SQLite fallback
    (`sqlite:///./waitlist.db`), documented as env.py-overridden.
  - `script_location = %(here)s/backend/alembic`, so the migration
    environment and versions live under `backend/` as scoped, while
    `alembic.ini` itself stays at the repo root alongside `pyproject.toml`
    (where `uv run alembic ...` is invoked from, both locally and in the
    `migrate` container).
- **`backend/alembic/versions/b38117986837_initial_schema.py`** —
  autogenerated against an empty scratch SQLite DB, then reviewed by hand:
  creates all 7 tables (`venues`, `staff_users`, `tables`,
  `waitlist_entries`, `large_party_enquiries`, `notifications`,
  `counters`) matching `backend/orm_models.py` field-for-field, including
  the `staff_users.username` and `waitlist_entries.accessToken` unique
  constraints.
- **`backend/main.py`** — removed the `Base.metadata.create_all(bind=engine)`
  call and the now-unused `Base` import from `create_app()`.
- **`tests/conftest.py`** — the unit-test `client` fixture now creates its
  own ephemeral per-test SQLite schema directly via
  `Base.metadata.create_all(bind=make_engine(database_url))` before calling
  `create_app()`. Alembic is the schema source of truth for
  production/Docker, but running full migrations for a throwaway per-test
  SQLite file is unnecessary ceremony — documented as such in the fixture's
  comment.
- **`docker-compose.yml`** — added a `migrate` service (same build as
  `app`, `command: alembic upgrade head`, same `DATABASE_URL`, depends on
  `postgres` being healthy). `app` now additionally depends on
  `migrate: condition: service_completed_successfully`, so migrations
  always run before the app container starts.
- **`Dockerfile`** — now also copies `alembic.ini` into the image
  (`COPY pyproject.toml uv.lock alembic.ini ./`) so the `migrate` service,
  built from the same image, can run `alembic upgrade head`.
- **`Makefile`** — `run` (local, non-Docker dev) now runs
  `uv run alembic upgrade head` before `uv run uvicorn ...`.

## Verification

- `uv run pytest` — **52 passed, 1 deselected** (the pre-existing
  Docker-only integration test), unchanged from before this session.
  Confirms removing `create_all()` from `main.py` didn't break the unit
  suite, since `tests/conftest.py` now creates its own schema.
- Ran `alembic upgrade head` by hand against a fresh, empty SQLite file
  (`DATABASE_URL=sqlite:////tmp/alembic_check.db uv run alembic upgrade
  head`) — succeeded, and inspecting the file afterward confirmed all 7
  expected tables (plus Alembic's own `alembic_version`) exist. Satisfies
  the "running `alembic upgrade head` successfully builds the database
  schema from scratch" acceptance criterion directly.
- `make e2e`: **could not complete in this sandbox.** `docker compose up
  -d --build` built both images fine, but the new `migrate` service timed
  out connecting to `postgres` on the compose bridge network. Confirmed
  this is the same pre-existing sandbox restriction already documented in
  [[issue-005_step-08_postgres-compose]] and
  [[issue-005_step-09_integration-and-e2e-tests]], not a regression from
  this change: `iptables -L -n` shows the `DOCKER` forward chain `DROP`s
  all bridge traffic except one allow-listed destination, so even a
  vanilla, unmodified `postgres:16-alpine` container run fresh on the same
  compose network can't reach another container by hostname *or* IP
  (`pg_isready`/DNS both fail). Cleaned up the stack afterward (`docker
  compose down -v`, plus a lingering `docker compose run` container
  removed by hand).
- `tests/integration/test_postgres_connectivity.py` was consequently not
  run either, for the same reason.
