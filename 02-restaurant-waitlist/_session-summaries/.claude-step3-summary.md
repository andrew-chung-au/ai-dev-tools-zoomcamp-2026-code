# Step 3 summary — OpenAPI contract from the frontend service layer

## What changed

Derived `openapi.yaml` (OpenAPI 3.0.3) directly from the frontend's
`WaitlistService` interface (`frontend/src/services/waitlistService.ts`),
cross-checked against `mockWaitlistService.ts` and the actual call sites in
`frontend/src/routes/*.tsx`. One HTTP operation per service method; request
and response schemas mirror the TypeScript types field-for-field (including
nullability). No backend or database code was written, and nothing was
staged or committed.

- 19 paths / 21 operations, one per `WaitlistService` method.
- 31 component schemas, covering every exported type in `waitlistService.ts`
  that is reachable from a method signature (`Venue`, `WaitlistEntry`,
  `Table`, `LargePartyEnquiry`, `Notification`, `GuestStatus`,
  `DashboardData`, request/result types, and the shared enums).
- `bearerAuth` (HTTP bearer) is the default security scheme; `POST
  /auth/login`, `GET /venue`, guest check-in (`POST /waitlist-entries`),
  guest status/cancel (`/guest/entries/{accessToken}...`), and
  `POST /large-party-enquiries` are marked `security: []` (public) because
  that's how they're actually used in the routes (e.g. `join.tsx` calls
  `getVenue()` before any login exists).
- Validated with `openapi-spec-validator` (installed ad hoc into the current
  environment, not added to the project) — passes with no errors.

## Mismatches between the frontend service and `_docs/specs.md`

The frontend service layer is a deliberately partial Module 2 slice. The
OpenAPI contract can only describe what the interface exposes, so the
following spec-required capabilities have **no corresponding method** in
`WaitlistService` and are therefore absent from `openapi.yaml`:

1. **Setup wizard / staff accounts (§6).** No `StaffUser` model, no
   "detect first run" / create-first-admin flow. `login()` accepts any
   non-empty username/password in the mock — there's no real credential
   check, no roles.
2. **Staff roles (§5, §6, §25).** `StaffSession` has no `role` field, so
   staff vs. admin/manager permission differences aren't modeled anywhere
   in the contract.
3. **Logo upload (§8).** `Venue.logoPlaceholderLabel` is just an alt-text
   string; there's no upload/replace/remove endpoint, no file validation
   (PNG/JPEG/WebP, 2 MB limit), despite this being in-scope for the MVP
   (only "antivirus scanning or cloud storage" is explicitly deferred).
4. **Table management (§9).** Only `listTables()` and
   `listCompatibleTables()` exist — no create/edit/activate/deactivate/
   remove. `Table` also only has a single `capacity`, not `Table`'s
   spec'd `minimum capacity` / `maximum capacity` pair, and has no
   `active` or `notes` fields.
5. **Opening schedule & manual override (§10).** `Venue.waitlistOpen` is a
   plain boolean. There's no weekly session schedule and no three-way
   override (`follow schedule` / `open now` / `closed now`) as §10
   requires.
6. **Party-size edits (§14, §15, §27).** The spec explicitly requires that
   staff can edit a party's size, preserving the ticket code and setting
   `review_required`. There is no `updateEntry`/`updatePartySize`-style
   method in `WaitlistService` — the mock only produces this state when
   seeding demo data, not through any exposed API.
7. **Explicit/manual review flags (§15).** Reasons like "staff explicitly
   requested review" or "other operational exception" have no
   corresponding method to set `reviewRequired`/`reviewReason` directly.
8. **Activity/audit log exposure (§25 `StatusEvent`/`ActivityLog`).**
   `ActivityEvent` is defined as a type and populated internally by the
   mock, but no `listActivity`/`getActivity` method exposes it — it can't
   appear in the contract.
9. **Notification provider metadata (§22).** `Notification` has no
   `providerMessageId` field, though the spec calls out "provider message
   identifier when available" as a stored field.
10. **Policy/message versioning (§21, §25).** The spec wants a stored
    `policy version` and `message template version`, plus a policy/message
    snapshot on each `WaitlistEntry` at acknowledgement/notify time.
    `VenueMessageSettings` and `WaitlistEntry` carry neither — edits to
    venue messages are just live overwrites with no history.
11. **Cancellation actor (§19).** The entry only records `cancelledAt`;
    there's no `cancelledBy`/actor field distinguishing a guest
    self-cancellation from a staff cancellation on the entry itself (the
    mock only encodes this in a free-text activity log entry, which per
    point 8 isn't exposed anyway).

None of these are bugs in the frontend — they're expected gaps at this
stage of the build (mocked frontend → OpenAPI → in-memory FastAPI →
SQLAlchemy, per §26). Flagging them here so the backend implementation step
and/or a future frontend task explicitly decides whether to extend the
service interface (and thus the contract) to cover them, rather than the
gap being discovered silently later.
